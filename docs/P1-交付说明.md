## 3. 数据结构与配置变化

| 项 | 变化 | 兼容性 |
| --- | --- | --- |
| `schema_version` | 1 → 2 → 3 | 只升不降；高于代码版本会明确报错 |
| 新索引 | `idx_chunks_content_proj`、`idx_sources_location`、`uq_chunks_live_content`（部分唯一索引：`invalidated_at='' AND content_hash<>''`） | 幂等迁移 |
| `chunks.content_hash` | 语义变为"纯正文指纹"（不再含 document_id） | 旧数据保留原值；新写入用新语义；需要一致口径时跑 `rebuild_vector_index()` |
| `chunk_id` | 由 `project + 内容指纹` 派生（同内容同项目 = 同一实体） | 旧 chunk_id 不变，只是新写入更稳定 |
| `security.allow_private_networks` | 新增，默认 `false` | 内网/离线场景需显式打开 |
| `security.max_redirects` | 新增，默认 `5`（0..20 校验） | — |
| `security.allowed_content_types` | 新增，默认 text/json/xml/xhtml/pdf | 需要抓其它类型时显式配置 |
| 工具参数 | `search_knowledge` 新增 `include_all_projects` | 缺省更严格（只看 global） |

## 4. 迁移、升级与回滚

**升级**：替换代码后首次启动自动跑 `migrate()`：
1. 建表（`IF NOT EXISTS`，不动现有数据）；
2. v2：补两个普通索引；
3. v3：同项目同内容的重复**活跃**片段 → 保留 verified/最高版本那条，其余标
   `superseded` + `superseded_by` 指向保留项（**不删除任何行**），再建部分唯一索引。

**回滚**：
- 代码：`git revert` 对应 commit；
- 数据：v3 只做"标记"不做删除，回滚后可人工把 `invalidated_at` 清空复原；
  仍建议升级前用 `backup_knowledge_base` 做一次备份（P7 会补备份校验）。

**注意**：`chunks.content_hash` 语义变化后，旧库中同内容不同文档的片段不会被自动合并——
这正是 v3 迁移做的事（标记为 superseded），但只对"已存在重复"生效；
历史数据若需要完全对齐，可在 P4 的增量重建任务里重算。

## 5. 测试执行结果

```
$ python -m pytest -q
151 passed in 13.5s          # 96 基线 + 55 新增

$ python examples/demo_end_to_end.py
chunks 5 · open_conflicts 1 · verified 1 · coverage 0.2   # 与 v1.1.0 一致
```

关键的"修复前会失败"用例：
- 覆盖式 upsert 保状态（原实现在 `BEFORE verified/v3 → AFTER pending/v1`）
- 配置单独不足以委派（原实现 `delegate_to_host=True`）
- 令牌不出现在工具返回值（原实现直接拼进错误消息）
- `manual_review` 无人工证据不升级（原实现 `verified/0.85`）
- 同内容不落第二份（原实现两行并存）
- `127.0.0.1:3090` 被拒（原实现直接请求）
- `snapshot()["llm_calls"] >= 1`（原实现恒为 0）
