# dsh-autolearn 架构审计报告

- 审计对象：`https://github.com/ILRI7512/dsh-autolearn` @ `1141a78`（v1.1.0）
- 审计日期：2026-10-20
- 审计范围：Python 引擎 11,000+ 行（core / sources / knowledge / storage / practice / security / tools / tests）+ 两个 Cordis 插件 + 配置与文档
- 方法：逐文件阅读 + pytest 基线 + **7 个可复现的行为实验**（能跑的都用跑的，不用"代码看起来像"下结论）
- 基线：`python -m pytest -q` → **96 passed**（9.76s）；`pnpm test` → node 语法 + 3 个自测全过

---

## 0. 结论

**骨架是合格的，纪律文档写得比实现好。真正的风险不在算法选型，而在写入语义与审批语义。**

三句话：

1. **"已核验"不可信**：`manual_review` / `static_analysis` / `update_knowledge` 三条路径都能在零独立证据下把知识推到 `verified`；覆盖式 upsert 还会把已验证知识静默打回未核验。
2. **"需用户确认"不成立**：生产部署路径上审批委派被一行环境变量短路（fail-open），而确认令牌明文回传给模型，模型可自己跑 CLI 批准。
3. **"学习闭环"有多处表演性完成**：主题化提取只有第一个任务真干活；短文档提取 0 条却记成功；文档改了旧知识不失效；批量去重根本不比内容哈希。

评：v1.1.0 是**可演示的原型**，不是**可靠的学习系统**。要达标必须做 P1-P4 的结构性修复，加功能只会放大问题。

同时必须肯定：README 对"哈希向量不是语义模型""进程级隔离不是沙箱""LLM 默认 mock"三条限制**如实披露**；`tool_risks.json` 与 63 个注册工具 **100% 对齐**（AST 逐项比对）；全仓**无** `except: pass`、**无**硬编码密钥、**无**机器专属绝对路径。这些是底子，优化时不能破坏。

## 2. 致命缺陷（P0，先修这些）

### F-01 覆盖式 upsert 摧毁核验状态与版本历史（数据不可逆）

`storage/vector_store.py:210-217` 命中同 `chunk_id` 直接 `upsert_chunk` 整行覆盖，`_coerce_chunk`（`:837-855`）用 `Chunk()` 默认值补齐缺失字段。**实测**：

```
BEFORE {'status':'verified','version':3,'verification_status':'verified','evidence_count':2,'confidence':0.9}
AFTER  {'status':'pending_verification','version':1,'verification_status':'unverified','evidence_count':0,'confidence':0.3}
chunk_versions 行数: 0
```

触发面：`save_knowledge` 允许调用方自带 `chunk_id`（`core/orchestrator.py:964`），工具参数允许额外字段（`tools/registry.py:90-93`）。一次工具调用即可把任意已验证知识打回未核验，且不留快照。

**修复**：upsert 必须"读-合并-写"——缺省字段取库内现值而非 dataclass 默认值；`status/verification_*` 只允许状态机迁移写入；任何状态下降前写 `chunk_versions` 快照。

### F-02 审批委派在生产路径上被短路（fail-open）

`plugins/autolearn/cordis.patch.yml:22` 无条件注入 `DSH_AL_HOST_APPROVAL: '1'` → `config.py:332-333` 写进 `security.delegate_approval_to_host` → `permissions.py:102-109` **第一分支就置 `delegate_to_host=True`**，`_host_gate_available()`（bundle 是否安装 / patch 是否 disabled / 心跳是否新鲜）永不执行。**实测**：无闸门、心跳 False 时 `destructive` 仍 `allowed=True, needs_confirmation=False`。

雪上加霜（T-03）：DSH 的 `scrubbedParentEnv` 丢弃所有 `DSH_` 前缀变量，MCP 行未传 `DSH_PROFILE_DIR` → `_host_gate_installed()` 在子进程**恒为 False**。于是：短路时不检查，不短路时永远检查失败——两条路都不通。

插件侧另有四处 fail-open：`index.js:220`（判定异常放行）、`:111`（prefix 不匹配静默放行）、`:62-75`（清单缺失只 warn）、`:196-199`（`ctx.on` 缺失时心跳定时器继续跑但闸门未挂）。

**修复**：删除配置直通分支，`_host_gate_available()` 为唯一判据；bundle 不注入该变量，改由 approval 插件运行期声明（心跳 + 代际）；闸门异常 fail-closed；MCP 行补传 `DSH_PROFILE_DIR`/`DSH_HOME`。

### F-03 确认令牌回传给模型，模型可自批（user-only 承诺破灭）

`tools/retrieval_tools.py:38-46`、`tools/verification_tools.py:35-40` 把 `request.token` **明文写进返回给模型的错误消息**；`main.py:247-250` 的 `confirmations approve <token>` 是模型可执行的普通 CLI。**端到端复现**：调用 → 取 token → 自跑 CLI 批准 → 带 `confirm_token` 重试 → `destructive` 成功。

README `:79-80` "审批是 user-only，智能体没有自我授权工具"在**工具表层面**成立（无 approve 工具），在**能力层面**不成立（模型有 shell）。

**修复**：令牌不出现在任何返回给模型的文本中；`approve` 校验调用者身份（TTY / 宿主 UI 回调）而非仅凭 token；令牌绑定 action+target+关键参数指纹。

### F-04 `verified` 有三条零证据捷径

| 捷径 | 证据 | 实测 |
| --- | --- | --- |
| `manual_review` 零证据 PASS | `verifier.py:189-192` `PASS if evidence_list else FAIL`，而 `_normalize_evidence:332-344` 无条件把条目自身 source 塞进 `evidence_list`，永不为空 | concept（质量 0.9）不传人工材料 → `pass/verified/0.85` |
| `static_analysis` 无 eval/TODO 即 PASS | `verifier.py:540-556` | code_example → `verified/L3/0.85` |
| `update_knowledge` 直写 status | `version_manager.py:35-45` fields 无白名单；`update_document:288-301` 的 setdefault 只在**内容变化时**执行 | `fields={"status":"verified","confidence":0.99}` → 立即 verified，无快照、无审计 |

现有 `test_model_self_review_does_not_verify` 之所以绿，是因为它用 `fact` + 质量 0.4，恰好绕开真实路径。

**修复**：`manual_review` 要求 `verifier="user"` 且证据来自外部渠道；`static_analysis` 只能给 `partial`，不得单独支撑 verified；`update_knowledge` 字段白名单，状态类字段只接受状态机迁移。

### F-05 `query()` 执行 DELETE 不提交，替换操作静默失效

`storage/vector_store.py:259`：`metadata.query("DELETE FROM chunks WHERE document_id=?", ...)`，而 `metadata_store.query()`（`:770-772`）只 `execute().fetchall()`，**不 commit**。**实测**：`in_transaction` False→True，行数变 0；重连后行数恢复为 1（删除被回滚）。

后果：`add_document(replace_existing=True)` 静默无效，并留下悬挂写事务持锁（并发写会 `database is locked`）。

**修复**：DML 走 `execute/commit` 通道；`query()` 加只读断言（遇 DML 直接抛错）。

### F-06 增量更新与去重的四个断点

1. **跨文档同内容永远去不了重**：`extractor.py:271` `content_hash = stable_hash(f"{document_id}|{chunk}")` —— 指纹混入 `document_id`。
2. **批量去重不比 hash**：`vector_store.py:586-612` 的 chunk_id-less 分支只走向量，`reason` 恒 `vector_similarity`；同内容仅标题不同 → `sim=0.909 < 0.94` → 漏检。
3. **重复只报告不拦截**：`add_chunks:194-205` 命中重复仍 `prepared.append` 并落库；`chunks` 表无 `(project_id, content_hash)` 唯一约束。
4. **文档变更后旧片段永不失效**：`ingest` 只追加新 document + 新 chunk，旧 chunk 不 `superseded`，v1/v2 并行存活，且都可能带 `verified` 身份被检索。

**修复**：指纹纯内容化（`content_fingerprint(chunk)`）；`chunk_id = project_id + content_hash`；唯一索引 + 命中即拒写（记 `duplicates` 表）；同 location 内容变化 → 新 document 版本 + 旧 chunk `superseded`（**绝不覆盖 verified**）。

## 7. 实施计划（P1-P8，与缺陷绑定）

### P1 修复数据与安全（F-01~F-06、H-03/H-04/H-05/H-06/H-07/H-12/H-13）
1. `upsert` 读-合并-写；状态/核验字段只走状态机；下降前写版本快照。
2. 审批：删配置直通，`_host_gate_available()` 为唯一判据；补传 `DSH_PROFILE_DIR`；闸门异常 fail-closed。
3. 令牌不回传模型；`approve` 校验调用者身份。
4. 封堵三条 verified 捷径；`update_knowledge` 字段白名单。
5. `query()` 只读断言；DML 走 commit 通道。
6. 指纹纯内容化 + 唯一索引 + 命中拒写 + 变更即失效。
7. SSRF 守卫（DNS 解析后逐 IP 判定 + 逐跳重定向复检）、`WRITE` 路径边界、robots 开关。
8. 预算接线（`consume_llm` + `llm_calls` 落库）。
9. 检索默认强制项目作用域（显式跨项目才放行）。

**验收**：新增 ≥10 个针对性失败用例；96 项基线不回归；`pytest` 全绿。

### P2 学习流程真实化（H-01/H-02/T-04）
1. EXTRACT 按 topic 取文档（source/document 打 topic 标签），或改为"单批提取 + 按主题核验"，二选一，不准继续假分主题。
2. 零产出必须告警 + `parse_status='no_knowledge'` + 任务 `result.reason`。
3. 8 阶段状态落库（`stage_state`），任务 result 必须带阶段进度。
4. `timeout_s` 执行期强制生效；依赖失败传播为 `blocked`。
5. `max_tasks` clamp；`TaskKind.READ` 实现或删除。

### P3 提取与分类 + 领域解耦（H-09，对应额外要求 1-10）
1. `domains/` 注册表：`DomainSpec{partition, topic_templates, classifier_keywords, quality_thresholds, knowledge_schema}`；核心只依赖 `DomainRegistry` 接口。
2. 内置领域降级为"内置领域包"，走同一注册 API；`Partition` 枚举改为字符串 key + 注册表（保留旧 key 别名）。
3. 工具 schema `enum`、CLI `choices`、`DOMAIN_TEMPLATES` 全部由注册表动态生成。
4. 领域级质量门槛与知识结构扩展；隔离检索 + 跨领域检索（返回强制带 `domain`/`partition`）。
5. 补齐 22 字段中缺失的 10 列，走 P1 引入的迁移机制。

### P4 去重 / 增量 / 来源追溯（F-06 的完成态）
1. 来源稳定标识（URL 归一化 + 本地 realpath）+ ETag/Last-Modified 条件请求。
2. 同 location 内容变化 → 新 document 版本 + 旧 chunk `superseded`。
3. 近重复：精确 hash + 向量相似度（阈值可配），标记 `duplicate_of`，不自动删。
4. 失效巡检任务（可关）。

### P5 检索
1. embedding 缓存表（`content_hash → vector`）；换 embedder 强制 rebuild。
2. 检索评估集（20-30 query/期望 chunk），`tests/test_retrieval_eval.py` 输出 recall@k / MRR / 误召回率，作为优化前后基线。
3. RRF 权重与 BM25 参数可配并记录基线。

### P6 质量评估
1. 质量分拆成可解释分量（来源/完整/时效/重复/验证），落 `quality_components`。
2. 程序化验证优先；`manual_review` 需 user 身份。
3. `level` 与 `status` 一致性校验；L4/L5 真正写入。

### P7 恢复 / 日志 / 可观测
1. 结构化 JSONL 日志（任务/预算/检索/失败）。
2. 并发保护：同一 `(project_id, location)` 处理中互斥；索引进程间锁 + 原子落盘。
3. 备份/恢复实测并加集成测试；备份校验 `schema_version` + `embedder_id`。

### P8 回归与交付
1. 全量 `pytest` + `pnpm test`。
2. 优化前后对比表（覆盖率 / 去重率 / recall@5 / 误召回 / 单轮耗时 / 预算准确性）。
3. 交付清单：文件列表、数据结构变化、配置变化、升级步骤、回滚方案、未完成事项。

## 8. 风险与回滚

| 变更 | 风险 | 回滚 |
| --- | --- | --- |
| upsert 读-合并-写（P1） | 存量重复行会暴露 | 迁移脚本先去重（保留 verified/最高版本）再收紧；旧库快照保留 |
| 内容指纹去耦（P1） | `chunk_id` 变化 → 旧向量失效 | `migrate_fingerprint()` 重算并重建索引；失败 `git revert` + 备份库恢复 |
| 唯一索引 | 存量重复导致建索引失败 | 先去重后建索引，分两步迁移 |
| 领域注册表（P3） | `Partition` 改动面大 | 旧 `Partition` 常量保留为别名，新代码走注册表 |
| SSRF / robots（P1） | 可能挡住合法内网/离线场景 | `security.allow_private_networks`（默认 false）、`security.respect_robots`（默认 true） |
| 审批收紧（P1） | 现有自动化流程会开始要确认 | 分模式：`auto` 保留宿主审批路径，`assisted` 强制本地令牌 |

所有改动在分支 `optimize/v1.2` 上进行，每阶段一个 commit 并附测试输出；`main` 不动。
